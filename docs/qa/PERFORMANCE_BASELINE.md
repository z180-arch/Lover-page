# 性能基线 · PERFORMANCE_BASELINE

> 本文件为「零构建静态站点」（入口 `index.html`，Vanilla JS + CSS + HTML，本地 `vendor/` 依赖，部署到 GitHub Pages）的性能基线。
> 它是后续性能优化的唯一对照依据。**宁可写「测不到」，也不写猜测的数字**——凡未能真实测出的项，均明确标注原因。
> 站点代码**未被本任务修改**；本文件记录的是两次真实浏览器测量。

### 1.1 指标采集方法

- **TTFB / FCP / CLS / DOM / 错误数**：取自 `performance.getEntriesByType('navigation')` / `'paint'` / `'layout-shift'` 与页面内置 QA 探针 `window.__lpErrors`（index.html:11-24）。
- **LCP**：`agent-browser vitals` 内置命令在纯加载下返回 `lcp: null`（其内部依赖 web-vitals，LCP/INP 仅首次用户输入或页面隐藏后才定稿）。因此 LCP/CLS 改用**注入式 `PerformanceObserver` 初始化脚本**（导航前注册，`buffered:true`）从浏览器读真实值。该脚本**只读不改**页面。
  - 该观察器在**少数冷启动的首跳导航**上会偶发漏捕 LCP（浏览器上下文冷启动与观察器注册的竞态，属工具产物，非站点问题），表现为个别 run 的 LCP = `NULL`，已在表中如实标注，中位数按「已捕获到的有效值」计算。
- **INP**：纯加载、无任何用户交互，**无法测得**（见 §4）。
- 每个视口 **≥ 3 次冷启动测量**，记录全部原始值并取中位数，避免单次网络/调度抖动污染结论。

## 3. 资源体积表（修复前基线，v=18）

`transfer` = 线上传输字节（含 HTTP 头），`decoded` = 解码后字节。本地服务器无 gzip，故 `transfer` 比线上偏大。

**统一口径（本节全部表格共用；2026-09-15 修正）**
- **单位 = KiB（1 KiB = 1024 字节）**，并附原始字节数以便复核。此前 §3.2/§3.5 的分组行误用 ÷1000（KB）而总计用 ÷1024（KiB），造成「分组之和 735.1 ＞ 总计 717.9」的 17.2 KiB 假差额——**是单位换算不一致，不是重复计入**（脚本已断言：分组之和恒等于子资源之和，见下）。
- **子资源** = `performance.getEntriesByType('resource')` 的**全部条目**（`initiatorType ∈ {script, link, img, audio, other}`），**不含 HTML 文档本身**。
- **首屏总 transfer** = 文档 `navigation.transferSize`（12074 B）+ 子资源 transfer 之和。
- **百分比分母 = 首屏总 transfer（含文档）**；为能核对，分组表单列「文档 (HTML)」一行，各行百分比合计 = 100%。
- **注意**：`bgm.mp3` 的元数据预载条目时有时无（网络层确实发出请求，但 Resource Timing 条目在部分 run 未落库，约 0.29 KiB），故子资源合计在不同 run 间可有 ≤0.29 KiB 波动。

## 5. 三条优化假设（按预期收益排序，均引自实测数字）

### 假设 1（已验证有效 ✅）：给「相邻照片预取」加可见性守卫，让两张相册图退出首屏
- **依据（修复前实测）**：`landscape-08.jpg`（146.97 KiB）+ `landscape-02.jpg`（92.40 KiB）合计 **239.36 KiB**，占首屏总 transfer 729.71 KiB 的 **32.80%**（§3.3）；二者只在第 6 步相册出现，首屏不展示却被 `network requests` 确认在首屏完整下载（耗时 135/86ms）。
- **根因（代码审查，非 lazy 能解）**：`renderPhoto()` 在 `DOMContentLoaded` 就会对**隐藏的** `#question6` 跑一次，其内部相邻照片预取用 **`new Image()`**，**完全不受 `loading="lazy"` 约束**——所以给 `<img>` 加 lazy 测出来是零效果。正确修复是在预取块外加可见性守卫（`script.js:531-547`）。
- **修复后实测结果（v=19）**：两张图**已从首屏消失**，首屏总 transfer 从 729.71 KiB 降到 **491.61 KiB（−32.63%）**，请求数 24→22。反向验证确认第 6 步仍能正常加载、切换（§3.5）。**假设成立。**
- **（原错误验证法的更正）**：首测曾把验证写成「给 `<img>` 加 `loading='lazy'`」。这是错的——`new Image()` 预取不受 lazy 约束。真实有效验证是：**进入第 6 步照片章（`appState.setState({currentStep:6})`，勿连点按钮以防撞 0×0 元素）后，用 Resource Timing 确认两张 landscape 图此时被请求且 `naturalWidth>0`，并确认「下一张」切换正常**——既证明字节下降，又证明功能未被删除以美化数字。

### 假设 2（待验证）：优化 LCP 主图 `redoute-gallica-bloom.webp`
- **依据**：该图 194.25 KiB（decoded 193.96 KiB），是 **LCP 元素**（§3.3），占首屏总 transfer 的 26.62%。当前不分视口统一下发 194 KiB——小屏严重过剩。手机端 LCP 中位数 2000ms（390×844）超「良好」阈值。
- **预期**：按视口尺寸重编码 + 转 AVIF/更小 WebP（小屏可降至 ~30–60 KiB），直接削减 LCP 字节与解码耗时。
- **验证**：重编码后在 320/390 视口重测，对比 LCP 与本国资源 transfer；并确认主图优先于其余图片（`fetchpriority="high"`）。
- **现状**：假设 1 落地后首屏带宽争用已减少，但本会话 LCP 捕获率低、动画抖动大，**LCP 是否随之改善暂不能断言**（§2.6）。本假设仍按原计划待独立验证。

### 假设 3（待验证）：延迟非首屏 JS 与 CSS
- **依据**：首屏 JS 共 222.82 KiB（15 文件，占首屏总 transfer 30.54%）。其中 `vendor/glightbox.min.js`（55.27 KiB，灯箱，仅第 6 步用）+ `vendor/mesh-gradient.esm.js`（26.71 KiB，装饰背景动画，非 LCP）+ `vendor/glightbox.min.css`（13.72 KiB）合计约 **95.70 KiB（13.11%）** 与首屏渲染无关，却随首屏同步阻塞下载/解析（多个脚本耗时 500–610ms）。
- **预期**：对 glightbox 与 mesh-gradient 改用 `defer`/动态 import，首屏 JS 解析量减约 95.7 KiB，load 事件（390×844 修复前中位数 3026ms）应提前。
- **验证**：延迟后对比 `load` 时间与 Resource Timing 中这些资源是否仍在首屏 block；确认第 6 步灯箱、背景动画在点开前已按需加载且功能正常。

## 7. 复现步骤

1. 起服务器：`python -m http.server 8901 --bind 127.0.0.1`（仓库根目录），`curl --noproxy 127.0.0.1` 确认 200。
2. 清空代理：`export http_proxy= https_proxy= HTTP_PROXY= HTTPS_PROXY=`（否则 Chrome 经代理访问本地失败）。
3. 首屏测量：每视口循环 ≥3 次：`close --all` → `--init-script <cwv-init>.js set viewport <w> <h>` → `open http://127.0.0.1:8901/` → `wait 7000` → `eval <full-metrics>.js` 读数。
4. LCP 经注入式 `PerformanceObserver`（`buffered:true`，监听 `largest-contentful-paint`/`paint`/`layout-shift`）读取；INP 纯加载无法测得。
5. 资源体积：`performance.getEntriesByType('resource')`；请求总数 `agent-browser network requests` 交叉验证。
6. **反向验证（验证「守卫」类修复时必做）**：`open` 首屏后 `eval appState.setState({currentStep:6})`（勿连点按钮）→ `wait 3500` → 读 Resource Timing 确认两张 `landscape` 图被请求、`#photoStage img` 的 `naturalWidth>0`、`contactSheet` 缩略图均加载 → `eval nextPhoto()` → 再读确认切换到下一张且仍正常。防止「靠删功能让数字变好看」。
7. 版本号：修复前 `?v=18`、修复后 `?v=19`；对比时确认 URL 带正确版本号。
