## 3. 决策

### **保留方案 A。不做技术栈迁移。**

理由（按权重）：

1. **当前架构尚未成为实际瓶颈。** 症状级证据：本轮一个 Agent 在单次会话内完成了
   主题层重构（新增 3 套主题 + 令牌层重写 + 跨主题缺陷修复）、章节声明化、
   面板溶解、无障碍修复，**零构建等待、零依赖安装、零编译错误**。
   如果架构是瓶颈，这个过程不会这么顺。

2. **本项目的核心价值是「可交付的静态体验」，不是「工程复杂度」。**
   收件人打开一个链接。任何形式的构建步骤都不改善这一点，
   只会让「改一句话」从「编辑 + 刷新」变成「编辑 + 等待 + 可能 build 失败」。

3. **模板层已经用 config + preset 表达了，且已验证有效**（ADR-005：三套主题
   客观指标两两不同）。方案 B/C/D 主要提供的收益（模块化、类型安全、组件复用）
   在**当前规模**（8 章、7 个源文件、无后端）下收益有限。

4. **依赖复杂度是长期负债。** 零依赖意味着这个仓库十年后仍然能用当时的浏览器打开。
   `node_modules` 意味着每几年必须做一次升级战役。

### 但——三个明确的「迁移触发条件」

如果**同时**满足其中任意一条，就应当重新评估：

| # | 触发条件 | 对应方案 |
|---|---|---|
| 1 | `script.js` 超过 **1400 行**，且已按 ADR-001 拆分过仍继续膨胀 | B（Vite + ESM，不要 React） |
| 2 | 需要**多个真实实例**（≥3 个不同人使用），且它们之间出现需要构建期解决的差异（如按素材色调自动选主题、批量生成） | D（Astro / 11ty，内容集合） |
| 3 | 出现真正的「在线编辑器」需求（用户在浏览器里改配置并预览） | B + 本地状态层；**仍然不引入后端**（先考虑 local-first + IndexedDB） |

迁移的**唯一允许路径**（`AGENTS.md` §3 铁律 1）：

```
建立依据（ADR）
  ↓
建立兼容层（保持现有体验不变）
  ↓
分模块迁移（每个模块独立 commit + 独立回归）
  ↓
保持现有体验（每步都跑 steps-regression + 视觉审计）
  ↓
完成
```

**禁止一次性 rewrite。** 不允许出现「先全部重写完再验证」的提交。

## 4. 数据库决策

**结论：不引入数据库。** 当前以及可预见的阶段，核心产品都是：

```
Config + Assets + Static Runtime
```

这三者已经能表达完整的产品。引入数据库的唯一动机是「云端」，
而云端的前提是「有多个用户 + 需要跨设备同步 + 需要账号」——这三者当前都不存在。

如果未来确实需要，评估顺序（从轻到重）：

| 方案 | 适用场景 | 代价 |
|---|---|---|
| **IndexedDB / local-first** | 本地草稿、离线编辑 | 零后端，但换设备就丢 |
| **Cloudflare Pages + KV/D1** | 静态托管 + 少量动态 | 需要后端心智，但基础设施仍在边缘 |
| **Supabase / Firebase** | 账号 + 云同步 + 行级权限 | 引入服务依赖与供应商锁定 |
| SQLite + 对象存储 | 自托管 | 需要运维 |

**当前不要为了「产品化」强行加入数据库。** 需要它的那天会很明显。

## 5. 已排除的具体方案（附原因）

| 方案 | 排除原因 |
|---|---|
| 引入 Vite 只为了「有 dev server」 | `python -m http.server` 已经是 dev server，且零配置 |
| 引入 React 做 8 章的交互 | 8 个章节的交互全是「显示一个、隐藏其它」+ 局部状态。
React 的收益（组件复用、状态管理）在这里小于它的成本（运行时 + hydration + 构建） |
| 引入状态管理库 | `window.appState` 95 行已覆盖需求（订阅 + 分派） |
| 引入 CSS 预处理器 | `:root` 令牌 + 自定义属性已是更好的方案（运行时可变，无需重新编译） |
| 引入 Tailwind | 本项目的视觉是**定制**的艺术方向，不是 utility 组合；且需要构建步骤 |
| 引入动画框架（GSAP / anime.js） | 现有动效全由 CSS keyframes + View Transitions 完成 |
| 引入 JSX / 模板字符串引擎 | 章节 DOM 是静态 HTML（可被浏览器直接解析、可被 SEO/读屏读取），
renderer 只填内容。模板引擎会把静态骨架变成运行时构造，是退步 |
| TypeScript | 在 7 个文件、无团队协作的规模下，类型收益 < 构建成本。
注意：**这是可逆决策** —— 一旦触发条件 1 成立，B 方案里 TS 是首选 |

## 6. 遗留的架构短板（诚实记录）

| 短板 | 影响 | 缓解 / 触发条件 |
|---|---|---|
| 全局命名空间（`window.*`） | 隐式依赖，无静态检查 | ADR-001：增量拆模块 + 保留旧全局名 |
| `script.js` 偏大（948 行） | 定位成本 | ADR-001：1400 行门槛触发强制拆分 |
| 无类型系统 | 字段改名靠人工搜索 | `DEFAULT_CONFIG` 形状校验 + 语义校验层（ADR-002 待做） |
| 无自动化单元测试 | 纯函数（如仪表角度计算）无回归保护 | 已有端到端浏览器 QA；纯函数单测可加 `node --test`（**不引入测试框架依赖**） |
| `?v=N` 手动递增 | 忘记递增 → 缓存导致「改了没生效」 | `AGENTS.md` §3 铁律 9 写进契约；未来可用 `index.html` 里的构建期哈希（但那需要构建 → 不做） |
